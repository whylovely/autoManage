# AutoJournal: план реализации, фазы 1 и 2

Этот файл — рабочий план первых двух фаз проекта `autojournal`.
Он написан как вводный маршрут для первого проекта на Go: что делать, в каком порядке, зачем это нужно и какой результат должен получиться после каждого шага.

Связанный документ с общей целевой архитектурой: [autojournal-architecture.md](./autojournal-architecture.md)

## Общая цель первых двух фаз

На выходе после Phase 1 и Phase 2 у проекта должен появиться:

- понятный каркас backend-части на Go;
- разложенный по папкам код без бизнес-логики в `main.go`;
- базовые доменные модели;
- интерфейсы репозиториев, чтобы потом можно было подключить SQLite без переделки всей архитектуры;
- минимальная точка входа для Wails, которая только собирает зависимости и связывает слои.

Пока без полноценной базы данных, без миграций и без настоящего UI для журнала. Это будет в следующих фазах.

## Как мыслить о структуре проекта

Для первого Go-проекта полезно держать простую схему:

- `cmd/` — точка входа приложения;
- `internal/domain/` — бизнес-сущности и интерфейсы;
- `internal/service/` — правила и сценарии работы приложения;
- `internal/storage/` — работа с SQLite;
- `internal/handler/` — слой, который Wails отдаёт во frontend;
- `frontend/` — интерфейс на Vue.

Главная идея: UI не должен знать, как устроена база. База не должна диктовать форму UI. Между ними должен быть backend со своими моделями и сервисами.

## Phase 1. Инициализация и инфраструктура

### Цель фазы

Подготовить проект так, чтобы дальше можно было спокойно добавлять код по слоям, не ломая структуру.

### Что уже есть

Сейчас в проекте уже есть:

- Wails-проект;
- `Go` модуль;
- `Vue/TypeScript` frontend;
- шаблонные файлы `main.go`, `app.go`, `HelloWorld.vue`.

Значит, не нужно делать `wails init` заново. Нужно привести шаблон к будущей архитектуре.

### Результат фазы

После завершения фазы структура должна стать примерно такой:

```text
autojournal/
├── cmd/
│   └── app/
│       └── main.go
├── internal/
│   ├── domain/
│   ├── handler/
│   ├── service/
│   ├── storage/
│   └── scheduler/
├── migrations/
├── frontend/
├── build/
├── go.mod
├── go.sum
├── wails.json
└── Makefile
```

### Шаг 1. Привести точки входа к нормальной структуре

#### Что делать

Перенести backend entrypoint из корня проекта в `cmd/app/main.go`.

#### Зачем

Когда проект маленький, `main.go` в корне ещё терпимо. Но как только появляются слои, зависимости и несколько пакетов, корень быстро превращается в свалку.

Папка `cmd/app` — стандартный и понятный для Go способ сказать: “здесь запускается приложение”.

#### Как делать

1. Создать папку `cmd/app/`.
2. Перенести туда содержимое текущего `main.go`.
3. Оставить в `main.go` корня либо ничего, либо удалить его совсем позже, когда убедишься, что сборка идёт через новый файл.

#### На что смотреть

В новом `cmd/app/main.go` не должно быть бизнес-логики. Только:

- создание зависимостей;
- создание `App`/handler;
- вызов `wails.Run(...)`.

### Шаг 2. Разложить backend по слоям

#### Что делать

Создать папки:

- `internal/domain`
- `internal/handler`
- `internal/service`
- `internal/storage`
- `internal/scheduler`
- `migrations`

#### Зачем

Это убирает хаос заранее. Даже если некоторые папки сначала будут почти пустые, структура уже начнёт диктовать правильное место для нового кода.

#### Практический совет

Не пытайся сразу заполнить все папки большим количеством файлов. В начале важнее правильные границы, а не объём кода.

### Шаг 3. Перенести текущий `App` в handler-слой

#### Что делать

Текущий `app.go` — это по смыслу не “ядро приложения”, а Wails binding layer. Его лучше превратить в `internal/handler/app.go`.

#### Зачем

Wails вызывает экспортируемые методы Go из frontend. Это граница между UI и backend. Ей место в `handler`, а не в корне проекта.

#### Что должно получиться

Файл `internal/handler/app.go` должен содержать:

- структуру `App`;
- `startup(ctx context.Context)`;
- временные экспортируемые методы для frontend;
- ссылки на сервисы, которые позже будут внедряться в `App`.

Примерно так по смыслу:

```go
type App struct {
	ctx            context.Context
	vehicleService *service.VehicleService
}
```

На этом этапе сервисы могут быть ещё `nil` или минимальными заглушками. Это нормально.

### Шаг 4. Подготовить пустой service-слой

#### Что делать

Создать первые файлы-заготовки:

- `internal/service/vehicle_service.go`
- `internal/service/expense_service.go`
- `internal/service/backup_service.go`

#### Зачем

Даже если логики внутри пока нет, появится правильное место, куда она пойдёт дальше. Это важно, чтобы не начать писать всё подряд в handler.

#### Что внутри на старте

На старте достаточно:

- объявить структуры сервисов;
- добавить конструкторы `New...Service(...)`;
- не писать лишнюю логику заранее.

Пример:

```go
type VehicleService struct {}

func NewVehicleService() *VehicleService {
	return &VehicleService{}
}
```

### Шаг 5. Подготовить пустой storage-слой

#### Что делать

Создать заготовки:

- `internal/storage/sqlite.go`
- `internal/storage/vehicle_repo.go`
- `internal/storage/expense_repo.go`
- `internal/storage/backup_repo.go`

#### Зачем

Позже Phase 3 подключит SQLite. Если папки и файлы уже есть, внедрение базы пройдёт проще.

#### Важно

Не надо в Phase 1 пытаться сразу писать настоящую работу с БД, если ты ещё не уверен в моделях и интерфейсах. Иначе начнёшь править код сразу в трёх местах.

### Шаг 6. Подготовить `Makefile`

#### Что делать

Добавить `Makefile` с простыми командами:

- `dev`
- `build`
- `test`

#### Зачем

Это снижает порог входа. Вместо запоминания длинных команд у тебя будет единая точка запуска.

#### Минимальный состав

```makefile
dev:
	wails dev

build:
	wails build

test:
	go test ./...
```

Если `wails` не в PATH, это вскроется сразу и будет проще починить окружение в начале, а не посреди разработки.

### Шаг 7. Проверить сборку после перестройки

#### Что делать

После каждого крупного перемещения файлов проверить:

```bash
go test ./...
```

и затем:

```bash
wails dev
```

#### Зачем

Главная ошибка новичков — сделать много перестроек сразу, а потом искать, где всё сломалось.

Лучший ритм:

1. маленькое изменение;
2. быстрая проверка;
3. следующее изменение.

### Phase 1: чек-лист готовности

- проект собирается после переноса entrypoint;
- Wails стартует;
- `App` лежит в `internal/handler`;
- созданы папки `domain/service/storage/handler/scheduler`;
- добавлен `Makefile`;
- в `main.go` нет бизнес-логики;
- backend-структура понятна даже без чтения всего проекта.

## Phase 2. Domain layer и интерфейсы

### Цель фазы

Описать предметную область проекта на языке Go, не привязываясь пока к SQLite и UI.

Это самая важная фаза для качества архитектуры. Если доменные модели слабые или неясные, дальше начнутся дубли, костыли и лишние переделки.

### Главный принцип фазы

`domain` должен описывать:

- что существует в системе;
- какие данные у этих сущностей есть;
- какие контракты нужны для работы с ними.

`domain` не должен описывать:

- SQL-запросы;
- детали Wails;
- детали Vue;
- файловые пути проекта;
- инфраструктурные зависимости.

## Какие сущности нужны

Для этого проекта базовый набор такой:

- `Vehicle`
- `Expense`
- `ExpenseCategory`
- `Backup`

### Шаг 1. Создать доменные файлы

#### Что делать

Добавить:

- `internal/domain/vehicle.go`
- `internal/domain/expense.go`
- `internal/domain/backup.go`

#### Зачем

Одна сущность — один файл. Так проще искать, читать и поддерживать код.

### Шаг 2. Описать структуры данных

#### Что делать

В каждом файле завести структуру с понятными полями.

#### Пример направления

Для `Vehicle`:

```go
type Vehicle struct {
	ID           int64
	VIN          string
	Make         string
	Model        string
	Year         int
	Color        string
	EngineVolume float64
	FuelType     string
	Odometer     int
	Notes        string
	CreatedAt    time.Time
	UpdatedAt    time.Time
}
```

Для `Expense`:

```go
type Expense struct {
	ID          int64
	VehicleID   int64
	CategoryID  int64
	Amount      float64
	Currency    string
	OdometerAt  int
	Date        time.Time
	Description string
	ReceiptPath string
	CreatedAt   time.Time
}
```

Для `Backup`:

```go
type Backup struct {
	ID        int64
	FilePath  string
	Note      string
	CreatedAt time.Time
}
```

#### Что означает `Backup` в этом проекте

На Phase 2 не нужно писать сам механизм резервного копирования. Здесь достаточно описать доменную сущность, которая хранит информацию о уже созданной копии:

- `ID` — идентификатор записи;
- `FilePath` — путь к файлу резервной копии;
- `Note` — необязательная заметка пользователя;
- `CreatedAt` — когда копия была создана.

Само создание backup-файла, экспорт и работа с SQLite пойдут позже, в storage/service-слой.

#### Практическое замечание

Для первого проекта лучше сразу использовать `time.Time`, а не строки дат в доменной модели. Строки удобны только в очень простых демо, но потом мешают валидации, сортировке и вычислениям.

### Шаг 3. Аккуратно выбрать типы полей

#### Что делать

На этом этапе нужно принять несколько базовых решений по типам.

#### Рекомендации

- `ID` — `int64`
- деньги — сначала можно `float64`, но надо помнить про погрешность
- дата и время — `time.Time`
- флаги активности — `bool`
- пробег — `int`

#### Важная оговорка про деньги

Для production-уровня деньги лучше хранить в минимальных единицах, например в копейках через `int64`.

Но для первого учебного прохода допустимы два варианта:

1. начать с `float64`, чтобы быстрее собрать проект;
2. сразу использовать `int64` в копейках, если хочешь дисциплину модели с самого начала.

Если выбирать учебно-практичный вариант, я бы советовал сразу использовать `int64` для суммы в минимальной валютной единице. Это чуть строже, но архитектурно правильнее.

### Шаг 4. Добавить теги, только если они реально нужны

#### Что делать

Если планируешь использовать `sqlx` и JSON-обмен, можно добавить теги:

```go
type Vehicle struct {
	ID   int64  `db:"id" json:"id"`
	Make string `db:"make" json:"make"`
}
```

#### Зачем

Это упростит mapping позже.

#### Но важно

Не перегружай модели тегами на все случаи жизни. Если пока не используешь `json` или `validate`, не обязательно вставлять их в каждое поле немедленно.

Для первого проекта лучше двигаться по принципу:

- сначала ясная модель;
- потом инфраструктурные теги;
- потом валидация.

### Шаг 5. Описать интерфейсы репозиториев

#### Что делать

Создать интерфейсы, которые будут определять контракты для хранения и чтения данных.

Например:

- `VehicleRepository`
- `ExpenseRepository`
- `BackupRepository`

#### Где хранить

Есть два нормальных варианта:

1. держать интерфейсы рядом с сущностями в `internal/domain`;
2. держать интерфейсы в отдельных файлах `vehicle_repository.go`, `expense_repository.go`.

Для новичка второй вариант обычно читается проще.

### Пример интерфейса

```go
type VehicleRepository interface {
	Create(ctx context.Context, vehicle *Vehicle) error
	Update(ctx context.Context, vehicle *Vehicle) error
	Delete(ctx context.Context, id int64) error
	GetByID(ctx context.Context, id int64) (*Vehicle, error)
	List(ctx context.Context) ([]Vehicle, error)
}
```

#### Почему это важно

Service-слой будет зависеть не от SQLite, а от интерфейса. Значит:

- код проще тестировать;
- реализацию БД можно менять;
- логика приложения не прилипает к SQL.

### Шаг 6. Продумать доменные правила заранее

#### Что делать

Ещё до service-слоя записать, какие ограничения вообще есть у сущностей.

#### Примеры правил

- `Vehicle.Make` не должен быть пустым;
- `Vehicle.Model` не должен быть пустым;
- `Vehicle.Year` должен быть в адекватном диапазоне;
- `Odometer` не может быть отрицательным;
- `Expense.Amount` должен быть больше нуля;
- `Backup.FilePath` не должен быть пустым.

#### Как использовать сейчас

На Phase 2 достаточно:

- либо зафиксировать правила комментариями;
- либо сделать простые методы проверки;
- либо просто явно записать их в этом плане и реализовать в сервисах позже.

Не надо смешивать доменные структуры и сложную валидацию слишком рано.

### Шаг 7. Не тащить Wails и SQL в domain

#### Что не делать

Не импортировать в `domain`:

- `github.com/wailsapp/wails/v2/...`
- `database/sql`
- `sqlx`
- frontend-зависимости

#### Почему

`domain` должен оставаться самым чистым слоем. Иначе он перестанет быть domain и станет смесью всего проекта сразу.

### Шаг 8. Подготовить сервисы к работе через интерфейсы

#### Что делать

После объявления репозиториев обновить service-заготовки так, чтобы они принимали интерфейсы через конструктор.

Пример направления:

```go
type VehicleService struct {
	repo domain.VehicleRepository
}

func NewVehicleService(repo domain.VehicleRepository) *VehicleService {
	return &VehicleService{repo: repo}
}
```

#### Зачем

Это первый нормальный dependency injection в проекте. Без фреймворков, просто и по-Go-шному.

### Phase 2: чек-лист готовности

- все базовые сущности описаны в `internal/domain`;
- у сущностей адекватные типы полей;
- интерфейсы репозиториев объявлены;
- service-слой зависит от интерфейсов, а не от SQLite;
- в `domain` нет импортов Wails и SQL-библиотек;
- понятно, какие доменные правила будут валидироваться позже.

## Рекомендуемый порядок работы

Чтобы не расползтись по нескольким направлениям сразу, лучше идти так:

1. Перенести entrypoint в `cmd/app`.
2. Создать папки `internal/...` и `migrations/`.
3. Перенести текущий `App` в `internal/handler`.
4. Создать пустые сервисы.
5. Создать доменные сущности.
6. Создать интерфейсы репозиториев.
7. Привязать сервисы к интерфейсам через конструкторы.
8. Проверить, что проект всё ещё собирается.

## Что не делать на этих фазах

- не писать реальные SQL-запросы раньше Phase 3;
- не делать сложный frontend раньше базового backend-каркаса;
- не смешивать domain и storage;
- не держать всю логику в Wails handler;
- не пытаться сразу реализовать все сущности полностью до первой сборки.

## Минимальный критерий успеха

Если после двух фаз ты можешь посмотреть на проект и быстро ответить:

- где точка входа;
- где domain;
- где service;
- где storage;
- где Wails handler;
- через какие интерфейсы backend будет работать с данными;

значит, фазы выполнены правильно.

## Что будет дальше после этих фаз

Следующая логичная стадия:

1. подключить SQLite;
2. написать миграции;
3. реализовать repository-слой;
4. подключить сервисы к реальным данным;
5. заменить шаблонный экран Wails на первый настоящий экран приложения.
