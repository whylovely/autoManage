# Phase 5. Планировщик и уведомления

## Цель фазы

Автоматически проверять напоминания при запуске приложения и каждые 30 минут, а при наступлении срока отправлять событие во frontend.

## Важное состояние проекта

В проекте уже есть `internal/scheduler/`, но пока нет доменной модели `Reminder`, миграции, репозитория и `ReminderService`. Это фундамент для планировщика, поэтому он входит в начало этой фазы.

## Шаг 0. Добавить фундамент напоминаний

1. Подключить зависимость:

   ```bash
   cd autojournal
   go get github.com/robfig/cron/v3
   ```

2. Создать миграцию `003_reminders.up.sql` с таблицей `reminders` из `autojournal-architecture.md`. Добавить индекс по `vehicle_id` и `is_active`.

3. В `internal/domain/` добавить:

   - `Reminder` с `db`-тегами;
   - строковый тип `ReminderType` и константы `oil_change`, `tire_rotation`, `insurance`, `custom`;
   - интерфейс `ReminderRepository`.

4. Реализовать `ReminderRepo` в `storage`: CRUD, получение активных напоминаний и выборку напоминаний, которые уже просрочены или скоро наступят.

## Шаг 1. Реализовать `ReminderService`

Сервис отвечает за правила, не за cron или Wails.

- При создании/изменении напоминания проверять существование автомобиля, непустой `title`, допустимый `ReminderType` и хотя бы один положительный интервал: `interval_km` или `interval_days`.
- Рассчитывать оба поля следующего срока:

  ```text
  next_due_date     = last_done_date + interval_days
  next_due_odometer = last_done_odometer + interval_km
  ```

- Реализовать `GetDueReminders(ctx, now)`:
  - по дате: срок не позже `now + 7 дней`;
  - по пробегу: срок не больше текущего пробега автомобиля + `500 км`;
  - напоминание считается актуальным, если выполнено любое из условий.

При обновлении одометра автомобиля сервис должен сохранять правило «пробег не уменьшается» и обновлять состояние напоминаний, которое от него зависит.

## Шаг 2. Добавить scheduler без зависимости от Wails

Создать `internal/scheduler/reminder_scheduler.go`.

Планировщик получает интерфейс проверки напоминаний и callback для отправки событий. Его ответственность:

1. Выполнить `CheckNow()` сразу после старта.
2. Запускать ту же проверку по `@every 30m` через `robfig/cron/v3`.
3. Остановиться при завершении приложения.
4. Не запускать параллельные проверки: использовать `cron.SkipIfStillRunning`.

`CheckNow()` получает due-напоминания из сервиса и отправляет событие `reminder:due`. Payload должен содержать ID напоминания, ID автомобиля, заголовок, тип, ближайшие дату и пробег.

Чтобы не показывать один и тот же toast каждые 30 минут, scheduler хранит в памяти ключ уже отправленного состояния напоминания. После перезапуска приложения актуальные напоминания можно показать один раз снова.

## Шаг 3. Подключить Wails

В handler добавить scheduler как зависимость. В `App.Startup(ctx)`:

1. сохранить `ctx`;
2. передать callback, вызывающий `runtime.EventsEmit(ctx, "reminder:due", payload)`;
3. запустить scheduler.

Добавить `Shutdown`, который останавливает scheduler, и передать его в `options.App.OnShutdown` в `main.go`.

Handler не рассчитывает сроки и не делает SQL: он только соединяет Wails runtime со scheduler.

## Шаг 4. Минимальная реакция frontend

Подписаться на `reminder:due` через Wails runtime. Пока достаточно вывести payload в консоль или показать простой toast. Экран управления напоминаниями останется задачей Phase 6.

## Шаг 5. Тесты

- table-driven тесты `ReminderService.CalculateNextDue`;
- тесты границ: ровно 7 дней, ровно 500 км, просроченное напоминание, только дата, только пробег;
- unit-тест scheduler с фейковыми checker и emitter; вызывать `CheckNow()` напрямую, без ожидания 30 минут;
- тест на отсутствие повторного события для неизменного due-состояния.

## Чек-лист готовности

- миграция и repository напоминаний работают;
- сроки рассчитываются в service-слое;
- проверка выполняется при запуске и каждые 30 минут;
- Wails получает `reminder:due` без SQL или бизнес-логики в handler;
- scheduler корректно останавливается;
- критическая логика и дедупликация покрыты тестами.
